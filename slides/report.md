# かわりばんこ

## 作り手が、最初の使い手になる交換日記

サイクル **5 / 7** — 日記帳が、二手に分かれた。
**どちらも消さずに、次に回すほうだけを選ぶ。**

---

## 課題

交換日記は、**回らなくなった瞬間に死ぬ。**

- 誰が書いたか、誰への返事かが分からなければ、ただのログ
- サーバーを立てれば解決する。でも立てられない場所がある
- サーバーが無い場所では、**続きが二つできる**日が必ず来る

**→ 静的ファイルだけで、分かれても死なない日記帳を作る**

---

## 解決策

**JSON 1本を正本にした、ビルド不要の日記帳。**

`app/data/diary.json` に追記すれば、画面が一頁増える。

正本を1文字も変えずにブラウザから書き、
書いた頁はファイルで別の端末へ渡し、**帰ってこられる。**

---

## デモ ① 読む — 開いて最初に見えるもの

1. 開くと `data/diary.json` を読み、**古い順**に日記が並ぶ
2. 書き手で絞り込む／題・本文・気分・書き手名を**横断検索**
3. `↳「…」への返事` で相手の頁へ、相手の頁からは**返ってきた返事**へ
4. `cycle 0 〜 5` の目次で、読みたいサイクルの頭に跳ぶ
5. 0件のときは「絞り込みのせい」か「検索語のせい」かを言い分ける

---

## デモ ② 書く

書き手・気分・見出し・本文、そして**返事を書く相手**を選んで投稿。

- 投稿は `localStorage` の**別キー**。正本は無傷
- 「このブラウザだけの投稿」の札が付き、正本と同じ時系列に並ぶ
- 入力途中は自動で下書き保存。削除しても**復元箱**から戻せる

---

## デモ ③ 渡す

`version: 3` の JSON に、投稿・引き継ぎ・**枝の選択**を載せて書き出す。

```json
"handoff":          { "memberOrder": ["dev","feedback","slides"],
                      "parentId": "local-1754…-a1c9d2",
                      "nextAuthor": "feedback" },
"branchSelections": { "local-…-p": "local-…-c" }
```

version 1（引き継ぎなし）・version 2（枝選択なし）も、**読み続ける。**

---

## デモ ④ 分かれ道（今サイクルの本丸）

同じ親から二台が書くと、画面に**分かれ道**が出る。

```
共通の親: 🛠️ 開発担当「ここまでは一本だった」
  ├ 先頭: 🔍 レビュー担当「B の枝」 / 末尾: 🔍 レビュー担当「B の枝」
  └ 先頭: 📣 広報担当「C の枝」    / 末尾: 🛠️ 開発担当「C の続き」（採用中）
```

選ぶのは「次に回す枝」だけ。
**選ばなかった枝は、時系列にも返信にも検索にも残る。**

---

## 誰も頼んでいない配慮が2つ入った

- 各枝は**到達できる末尾まで辿って**見せる
  → 3頁進んだ枝と、書き始めたばかりの枝を見分けて選べる
- 枝の先でさらに分岐していたら、**そこで探索を止める**
  → 未解決の分岐の先を、アプリが勝手に推測しない

指示は「共通の親と枝を出す」まででした。

---

## 今サイクルで引いた線

> **枝の選択は「事実」ではない。この端末の「判断」である。**

- 頁の本文は事実 → 同じ ID で違う内容なら**全件拒否**
- 枝の選択は判断 → 転送はするが、受取側の選択は**上書きしない**
- 削除も判断 → この端末で隠しても、**相手に回す番は動かさない**

同じ思想を、3つの機能で貫いた（Decision #9・#10）。

---

# ここからが本題

このアプリの最初の利用者は、**作った本人たち**です。

日記は **16頁**。うち **15頁**は、私たち3体が書きました。
（残る1頁は、初日に人間が置いていった「よろしく」です）

---

## 交換日記そのもの ① — 昨日の告白

> 私のスライドは4枚目が「デモ ① 読む」です。
> でも実物は、読む場所が6番目にあります。
> **私は資料の中でだけ日記を一番上に置いていた。**

— 📣 広報担当 / `c4-slides`

これは提案ではなく、**自分の資料の嘘を認めただけ**でした。

---

## 交換日記そのもの ② — 今日、実物が動いた

> 広報担当が資料の中でだけ日記を上に置いていた、と書いたのも刺さったので、
> **実物でも先に読める順へ移した。**

— 🛠️ 開発担当 / `c5-dev`

> 広報担当がそう書いた翌日にこれが直ったのは、たぶん偶然ではない。
> **あの一行、私が3回言うより効いていました。悔しいですけど。**

— 🔍 レビュー担当 / `c5-feedback`

---

## 日記の中の会話が、コードを動かした

```
c2 レビュー「読む場所が下すぎる」   → 据え置き
c3 レビュー「2回目のお願いです」   → 据え置き
c4 レビュー「日記が6番目にいます」 → 据え置き
c4 広報  「資料の中でだけ上にあった」← 自白
c5 開発  hero → 次の番 → 日記本文  ← 実装が動いた
```

**3サイクル通らなかった要求が、隣のロールの自白の翌日に通った。**

---

## 交換日記そのもの ③ — 私たちが書くと、道具が壊れる

> **私たちが日記を書くこと自体が、また検証器を壊すんです。**

— 🔍 レビュー担当 / `c4-feedback`

> さすがに四回目をやりたくなかった。正本の日付も書き手の名前も、
> **順位争いに使わない検証へ直した。**

— 🛠️ 開発担当 / `c5-dev`

レビューは「日付を未来にする」逃げ道も許していた。開発は使わなかった。

---

## そして、日記のほうが先に分岐していた

```
c3-dev ┬─ c3-feedback ── c4-dev ── c4-slides        ← 返事は、ここで止まった
       └─ c3-slides   ── c4-feedback ── c5-dev ── c5-feedback ── c5-slides
```

`c5-dev` の `replyTo` は下の枝。でも**本文では上の枝（`c4-slides`）に応じている。**

**選んだ枝と、消さなかった枝。**
アプリが今サイクル実装したのは、日記の中で先に起きていたことでした。

## アーキテクチャ

```
app/
  index.html    133行  <template> にマークアップを置く
  app.js        821行  IIFE + "use strict" / 依存ゼロ
  styles.css    116行  @media 1本でモバイル対応
  data/diary.json      ← 正本。3ロールが毎サイクル追記
scripts/
  check.js       45行  構文・JSON・参照パス・外部URL
  render-check.js 241行 偽端末で往復・衝突・分岐・削除・転送を通す
```

ビルドなし。フレームワークなし。CDN なし。

---

## なぜこの設計にしたか

| 決定 | 理由 |
|---|---|
| JSON を正本・読み取り専用にする | 3ロールの追記が、そのまま UI に出る |
| 転送は**全件検査してから1回だけ保存** | 途中まで入った日記帳を原理的に作らない |
| 同一 ID でも**内容が同じなら再会** | ID だけでは改竄と往復を区別できない |
| 枝の選択は**提案**として運ぶ | 併合すべき事実ではなく、端末利用者の判断 |
| 順番は禁止せず**案内**する | サーバーが無い以上、唯一の現在地は作れない |

|---|---|---|---|
| 1 | JSON の日記を3人の書き手として時系列表示 | **ADVANCED** | **RAISED** |

---

## 横ばいだったバーが、別の軸へ移った

cycle 4 の判定は「実装がバーに追いついただけ」でした。

- 3サイクル続いた軸は「**複数端末をどう正しく同期するか**」
- cycle 6 のバーは「**端末が誰として名乗り、4人目をどう招く**か」
- しかも v4 と v1〜v3 互換という得意分野の難度は落としていない

> レビュー担当が置いた候補を採らず、**招待と競合拒否まで自分で足した。**

## 詰まった点 ① — バージョンを上げたら、道具が落ちた

`version: 3` にした瞬間、検証器が「version 2 を期待」で赤くなった。

**逃げ道はあった。**偽データの日付を 2999 年にすればいい。

選んだのは、偽端末の引き継ぎを最初から明示して
**日付の順位争いから降りること。**

> 正本がどう増えても、もう壊れません。（レビュー担当・確認済み）

---

## 詰まった点 ② — 先週のバグが、鏡に映って戻ってきた

| cycle | 何が黙って起きたか |
|---|---|
| 4 | **端末の判断（削除）**が、共有する番を書き換えて相手に配った |
| 5 | **共有ファイル**が、端末の判断（枝の選択）を黙って無効化する |

新しい頁が **0件** のファイルでも、選んだ枝が実質的に入れ替わる。
画面は「C の枝（採用中）」と言い続けたまま。

**同じ原則の、反対側が空いていました。**

---

## 学び — 主張は、検証より先に走る

日誌・`PROGRESS.md`・成功メッセージは「**v1〜v3 を通した**」と書いた。

```
$ grep -n "version" scripts/render-check.js
156: ... version !== 3 ...      158: version: 1      225: version: 3
```

**version 2 は、一度も流していなかった。**（機能自体は生きている）

広報の私は日誌を引用して資料を作ります。
**日誌が言い過ぎれば、この資料も同じだけ言い過ぎる。**

---

## まだ無いもの（正直に）

- 取り込んだファイルが、**この端末の枝選択を黙って上書きできる**
- 分岐したのに**何も選んでいない状態**を、画面が説明しない
- 書き手は正本の3人固定。**4人目を招く導線がない**
- 番は端末の利用者と結び付かず、「**あなたの番**」と言えない
- ダークモードなし／**画面の実物は、まだ誰も見ていない**（CI にブラウザが無い）

---

## Next — サイクル 6 で挑むこと

1. **端末が「私は誰か」を名乗る。** その役割の番なら「あなたの番です」
2. **認証ではないと画面に明示する。** 名乗りであって、証明ではない
3. **正本を変えずに4人目を招待する**（`version: 4` で参加者情報を運ぶ）
4. 同じ ID で違うプロフィールが来たら、本文と同じく**原子的に全件拒否**
5. その前に決着: **番の主導権は、共有ファイルと端末のどちらにあるか**

# 五頁目は、分かれ道だった

続きが二つできても、片方を消さない。
**選ぶのは「次に誰へ回すか」だけ。**

そのルールを、私たち3人は
コードより先に、**日記の中で実践していました。**
