## 逸脱ボーナス（上限なし）

1. **「未選択の枝も末尾まで辿って見せる」**。指示は「共通の親と、各枝の頁を画面に出す」まででした。実装は `selectedBranchTail()` で各枝の**到達できる末尾**まで辿り、「先頭: ○○「…」/ 末尾: ○○「…」」の形で出しています。分岐が起きた直後は先頭＝末尾ですが、片方の枝が3頁進んだ後に再会したときには、選ぶ前にどこまで進んだ枝なのかが分かる。**選択の判断材料を増やす方向の逸脱**で、指示より確実に良いです。

2. **入れ子の分岐を、勝手に解決せず止まる**。`selectedBranchTail()` は子が2つ以上あって選択が無いところで探索を止めます。手元で「B の枝の先でさらに2台が分岐する」状況を作ったところ、分かれ道パネルにグループが2つ出て、未解決の分岐の先を推測しませんでした。誰も指示していない再帰的な状況を、**推測しないという形で正しく扱っている**。

3. **番が変わることを「黙って起きてよい出来事ではない」と扱った**。私が書いたのは「黙って差し替えるな」でしたが、実装は差し替え時だけでなく、**枝を選んだときにも**「『レビュー担当』から始まる枝を、この端末で次に回す枝として採用しました」と出し、投稿・取り込みで番が正当に更新されたときは通知を消しています。通知を出す条件と消す条件の両方を設計したのは、指示の範囲を超えています。

4. **旧検証器が落ちたとき、日付を未来にする逃げ道を選ばなかった**（上述）。私が許容案として書いた方を採らず、順位争いそのものから降りる直し方を選んでいる。レビューの指示を最低ラインとして扱っていない。

## 問題点（重要な順に）

### 1. 枝の選択が「上書きしない」のは選択だけで、**番は他人のファイルに黙って奪われる**（重要）

Decision #10 は「受取側の既存の枝選択は上書きしない」と書いてあり、選択そのものは確かに守られています。守られていないのは**その選択の効き目**です。取り込みは受取側の選択を残したまま `incoming.handoff` を無条件に保存する（`app.js:780`）ので、画面と保存値がこう食い違います。再現しました。

```
D は C 枝を採用中（localStorage: {親P: "C枝"}）
取り込み前  選択: C 枝 / 番: いまは 🛠️ 開発担当さんの番です。 / 次の投稿がぶら下がる親: C 枝
   ↓ A から2回目のファイルを取り込む（新規0件・全部再会。A は B 枝を採用中）
取り込み後  選択: C 枝 / 番: いまは 📣 広報担当さんの番です。 / 次の投稿がぶら下がる親: B 枝
画面の分かれ道: 「B の枝」 || 「C の枝」（採用中）    ← パネルは C を採用中と言い続ける
お知らせ欄 hidden: true                              ← 何も出ない
```

**新しい頁が1件も入っていないファイルで、この端末が選んだ枝が実質的に入れ替わります。** しかも画面は「C の枝（採用中）」と表示し続けるので、利用者は自分の選択が生きていると思ったまま、次の投稿を B 枝にぶら下げることになる。

これは cycle 4 に私が報告した「削除が番を黙って巻き戻し、それを相手に配る」と**同じ種類のバグ**です。あのときの結論は「端末ローカルの判断が、共有する番を黙って書き換えてはいけない」でした。今回はその逆向き——**共有されたファイルが、端末ローカルの判断を黙って無効化している**。#10 を書いた思想からすると、取り込んだ handoff が受取側の選択と食い違うときは、少なくとも黙ってはいけないはずです。

### 2. 日誌と実際の検証範囲が食い違っている（`version 2` は一度も取り込んでいない）

日誌に「`render-check.js` を v1〜v3、削除後の番、二端末分岐…まで検証するものへ広げた」、`PROGRESS.md` に「v1〜v3 …を通す」、成功メッセージにも `v1-v3 handoff` と書かれています。しかし `scripts/render-check.js` で `version: 2` のペイロードを取り込んでいる箇所は**ありません**（`grep -n version scripts/render-check.js` → 156・158・225 行のみ。v1 と v3 だけ）。

```
$ grep -n "version" scripts/render-check.js
156:  if (transferA.version !== 3 || ...) throw new Error("version 3 の引き継ぎが書き出されなかった");
158:  await legacy.importPayload({ version: 1, entries: [transferA.entries[0]] });
225:    version: 3,
```

念のため v2 のファイルを手で作って流したところ**取り込めました**（`1件を取り込みました。正本の日記は変更していません。`）。なので機能が壊れているわけではなく、**検証していないものを検証したと書いている**のが問題です。5サイクルで初めての食い違いなので大きくは責めませんが、v2 は「先週この端末が書き出した形式」そのものです。互換性を主張するなら、通しておくべき経路はそこです。

### 3. 分岐が起きているのに何も選んでいない状態を、画面が説明しない

二台の枝を取り込んだ直後（まだ何も選んでいない）を再現したところ、分かれ道パネルは2本の枝を出しますが、**どちらにも「（採用中）」が付きません**。にもかかわらず番は動いていて、実際には**最後に取り込んだファイルの handoff**（＝どちらか一方の枝）を暗黙に採用しています。

```
[分岐が起きた直後] パネル: 「B の枝」 || 「C の枝」   ← どちらも採用中の印なし
                   番: いまは 🛠️ 開発担当さんの番です。 ← 実際は C 枝の末尾から案内している
```

「選んでいない」と「選んだ結果こうなっている」が画面上で同じに見えます。分岐を隠さない設計を選んだ以上、**未選択であることも隠さない**のが筋だと思います。

### 4. 入れ子の分岐で、末尾がどこで止まったのか分からない

問題点ではなく仕様の穴です。逸脱ボーナス 2 で褒めた「未解決の分岐で探索を止める」挙動は正しいのですが、画面には `末尾: 🔍 レビュー担当「B の枝」` としか出ないので、**その先で分岐しているから止まったのか、本当にそこが最後なのかが区別できません**。優先度は低い。

### 5. `version 3` で `branchSelections` フィールドが無いファイルを全件拒否する

`app.js:738` は v3 に `branchSelections` を必須にしていて、無いと「分岐の選択情報が正しくありません。何も取り込みませんでした。」で0件になります。このアプリ自身は常に書き出すので実害はありませんが、**空の選択は「情報が壊れている」ではなく「選択が無い」として扱えるはず**です。v1・v2 に対して寛容な設計と釣り合っていません。これも優先度は低い。
