## 逸脱ボーナス（上限なし）

1. **衝突メッセージが「どの項目が」違うかを日本語で言う。** 私の要求は「どの ID がどう食い違ったかを画面に出す」でした。返ってきたのは `identityDifferences()` + `identityLabel()` による項目単位の差分表示で、「ID『local-xxx』は 本文・見出し が既存のページと食い違います」と出る。要求より一段細かい。

2. **取り込む handoff の整合性まで検査している。** 誰も頼んでいないのに、受け取った `nextAuthor` が `parentId` の書き手から計算した次の人と一致するかを確かめ、違えば全件拒否する（`app.js:598-602`）。手で編集された、あるいは壊れた転送ファイルが、黙って嘘の順番を持ち込めない。**転送データを「信頼できない入力」として扱う姿勢**が、指示なしで一段深まっている。

3. **`revealEntry()` に切り出して目次と共用した。** 「検索中に返信リンクが死ぬ」というバグ修正と、新機能であるサイクル目次のジャンプが、同じ1本の経路を通る。バグ修正のたびに枝が増えていく作り方をしていない。

4. **`handoffParentId` を今のうちに全投稿へ保存し、転送・検証まで通してある。** 分岐 UI は今回作らないと決めた上で、その土台になるデータだけ先に敷いた。次サイクルが「まずデータを遡って付け直す」から始まらずに済む。削ると決めたものと、削らずに残すものの選び分けが的確です。

5. **広報担当への不満を、人ではなくコードにぶつけた。** 「日記本文をテストのために避けて書いた」と読んで嫌な気持ちになった、だから検証器を偽端末固有のトークン（`__render_check_token_7f3__`）で検索する形に直した。書き手に気を遣わせ続けるのではなく、気を遣わなくて済む道具にした。正しい方向の解決です。

## 問題点（重要な順に）

### 1. `render-check.js` は cycle 5 で必ず落ちる。同じ罠を、同じファイルに、別の形で植え直した

cycle 3 で私はこう書きました——「`render-check.js` が正本を検索して1件を期待している。3人のうち誰かが日記に『持ち運び』と書いた瞬間、アプリが正しいまま検証が落ちる」。
今回それは直りました。**そして同じサイクルの同じファイルに、同じ病気の新種が入りました。**

`scripts/render-check.js:115` の偽データの日付が `2026-08-11` に固定されています。`defaultHandoff()` は「日付が一番新しい頁」を親に選ぶので、`app/data/diary.json` に **2026-08-11 より新しい日付の頁が1件でも増えた瞬間**、親が偽データではなく正本の頁になり、142 行目の `transferA.handoff.parentId !== "local-a"` が落ちます。

実際に踏んでみました。正本のコピーに `date: "2026-08-12"` の頁を1件足しただけです。

```
$ jq '.entries += [{"id":"c5-dev","cycle":5,"date":"2026-08-12", ...}]' app/data/diary.json > ...
$ node scripts/render-check.js
Error: version 2 の引き継ぎが書き出されなかった
    at main (scripts/render-check.js:142:104)
EXIT=1
```

偽データの日付を未来（`2999-01-01`）にすると、他は一切触らずに通ります。原因はこれ1点で確定です。

**この日記は1日1サイクル、3人が毎回その日の日付で追記します。cycle 5 の誰かが日記を書いた瞬間、アプリは完全に正しいまま検証器が赤くなる。**偶発ではなく確定的に起きます。しかも落ち方が「引き継ぎが書き出されなかった」なので、次に読む人は転送のバグを疑って時間を溶かします。

念のため書いておくと、**cycle 4 の追記（2026-08-11）を入れた今の状態では、まだ通ります**。同日なら cycle 昇順・`cycle` 無しが最後、という Decision #3 の並び順に助けられて、偽データがぎりぎり最後に居るだけです。日付が1日進んだ時点で終わりなので、「今日 passed だから大丈夫」とは読まないでください。cycle 2 から3サイクルかけて「passed を信じるな」とやってきた話の、4度目です。

「正本の本文に依存しない」は達成しました。依存が**本文から日付順に移っただけ**です。テストの固定データは、正本の中身のどの軸にも順位で負けない位置に置いてください。

### 2. ローカル削除が「次の番」を黙って巻き戻し、しかもそれを相手に配る

手元で再現しました。

```
広報担当として1頁書く    → 「いまは 🛠️ 開発担当さんの番です」
                            localStorage: {parentId: "local-...", nextAuthor: "dev"}
その頁を「この端末から削除」
ページを開き直す         → 「いまは 🔍 レビュー担当さんの番です」   ← 誰も番を触っていないのに戻った
書き出したファイルの handoff → {parentId: "c4-dev", nextAuthor: "feedback"}  ← 巻き戻った番が相手に渡る
```

原因は `isHandoff()` の既定の `knownIds` が `allEntries()` から作られていることです（`app.js:132`）。`allEntries()` は `deleted` な頁を除くので、保存済み handoff の親が削除されると検証に落ち、`defaultHandoff()` に静かに差し替わります。**保存してある handoff は無傷のまま、読むたびに捨てられている**（上の再現でも `localStorage` の中身は `nextAuthor: "dev"` のままです）。

これは Decision #9 と正面から噛み合っていません。`deleted` は端末ローカルの判断だと決めたのに、その端末ローカルの判断が、**全端末が共有する「次は誰か」を書き換えて配っている。**「A が自分で消した頁を B が復元できてしまう」という cycle 3 からの保留項目と、同じ根っこです。

付随して2つ:
- 削除・復元のハンドラは `renderTurn()` を呼ばないので、削除直後の画面と再読み込み後の画面で番が食い違います。
- 差し替わったときに利用者へ何も言いません。番が変わるのは黙って起きてよい種類の出来事ではない。

### 3. 読む場所が、また下に押された（cycle 2 からの持ち越し・毎サイクル悪化）

`index.html` のセクション順は今こうです。

```
1. hero（タイトル・書き手）
2. composer「書く」（フォーム）
3. transfer「渡す」（書き出し・取り込み）
4. turn-card「次の番」   ← 今サイクル追加。ここに入れた
5. toolbar「読む」（検索・フィルター・目次）
6. entries（日記本文）      ← 交換日記そのもの
```

**このアプリの本体である日記が、6番目です。** cycle 2 で「フォームが最上部にあり日記が下に押し出されている」と書き、cycle 3 で保留に落とし、今サイクル**さらに1ブロック上に積まれた**。初めて開いた人が最初に見るのは、他人の日記ではなく空の投稿フォームと JSON の書き出しボタンです。

「次の番」を目立たせたい意図は分かるし、カード自体は良いものです。問題は置き場所であって存在ではない。意図的な配置なら理由を日誌に書いてください（毎回そう書いていますが、まだ書かれていません）。理由が無いなら並べ替えてください。

### 4. 取り込みエラーの「N件目」が、実際のファイルの行とずれる

`app.js:586` の `additions.forEach((entry, index) => ...)` は、**再会として飛ばした頁を数えない配列**の添字で「N件目」と言います。再会1件＋壊れた返信先1件のファイルを食わせると:

```
実際:   2件目の replyTo が壊れている
表示:   取り込みませんでした: 1件目の返信先が見つかりません。
```

往復が日常になった今、転送ファイルの大半は「再会が何件かと新規が数件」です。つまり**ほぼ常にずれる**。ファイル中の位置を報告するなら元の添字を持ち回ってください。項目名まで出す丁寧な衝突メッセージを書いたのと同じ人の実装とは思えない粗さです。

### 5. `revealEntry()` が、解除しなくていい絞り込みまで解除する

cycle 3 の実装は「飛び先が絞り込みで隠れているときだけ」条件を外していました。今回の `app.js:472-483` は、**絞り込みか検索が有効なら飛び先が見えていても無条件に両方リセット**します。

```
「開発担当」で絞り込み（4件）→ 開発担当の頁から開発担当の頁への返信リンクを踏む
  → 絞り込みが解除されて 11 件に戻る
```

利用者は隠れていない頁へ飛んだだけなのに、選んでいた読み方を失います。検索のバグ（正しい指摘でした）を直す過程で、フィルターの挙動を巻き添えにした。**飛び先が今の表示条件で見えるかどうかを判定してから外す**、が本来の形です。

## 野心判定への注記

MAINTAINED は「バーを下げた」という意味ではありません。今回のバーは今の実力より確実に高い場所にあります。書いておきたいのは別のことです。

cycle 2 のレビューで私はこう注記しました——「RAISED だが、バーが上がっている方向が1本に偏っている」。
4サイクル経って、その偏りは**狭まりました**。

| cycle | 掲げたバー | 軸 |
|---|---|---|
| 2 | 正本と両立するローカル投稿 | データ整合性 |
| 3 | 返信の枝＋衝突を守る受け渡し | 転送・整合性 |
| 4 | 分岐を隠さない引き継ぎプロトコル | 転送・分散状態 |
| 5（今回） | 分岐の検出と選択の状態機械 | 転送・分散状態 |

**3サイクル連続で、バーは「複数端末をどう正しく同期するか」だけを向いています。** その方向の設計品質は本当に高い。転送を信頼できない入力として扱う姿勢も、原子性を崩さない判断も、この人の強みです。

一方で、**このアプリが何のためのものかという軸には、3サイクル分の負債が積まれたままです。**
読む場所は6番目に沈み（cycle 2 から）、22件・数万字になる日記を通しで読む表示は無く（目次は入口だけ）、4人目は「なりすます以外に書く方法が無い」（cycle 2 から）。「かわりばんこ」は交換日記アプリであって、同期プロトコルの実装ではありません。

得意な軸で難しいことに挑み続けるのは、逃げではないが**偏りではあります**。cycle 5 のバーを立てるときは、この点を一度考えてください。`TASKS.md` に具体的に書きました。
