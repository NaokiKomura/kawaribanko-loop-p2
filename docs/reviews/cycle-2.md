## 問題点（重要な順に）

### 1. `scripts/check.sh` は、4つの検査のうち2つを黙ってスキップしたまま「passed」と表示する

**これが今回いちばん重い指摘。** この実行環境には `rg`（ripgrep）が**インストールされていない**。私が確認した:

```
$ sh scripts/check.sh
scripts/check.sh: 7: rg: not found
scripts/check.sh: 20: rg: not found
check.sh: syntax, JSON, local paths, and runtime URLs passed
exit=0
```

`set -eu` を書いてあるのに止まらない。理由は2つあり、どちらも典型的な罠である。

- **7行目**は `references=$(rg ... | sed ... | sort -u)` というパイプライン。`set -e` が見るのはパイプラインの**最後**のコマンド（`sort -u`）の終了ステータスで、これは成功する。よって `rg` が 127 で死んでも止まらず、`references` が空になる。空なので `for` ループが一度も回らず、**参照ファイルの存在確認が丸ごと行われない。**
- **20行目**は `if rg ...; then` という条件式。`if` の条件部では `set -e` が無効になる。`rg` が 127 で死ぬと「マッチ無し」と同じ扱いになり、**外部 URL の検査が「外部 URL は見つかりませんでした」として通過する。**

実証した。`styles.css` に `https://example.com/x.css` を書き足し、`index.html` の `href="styles.css"` を存在しない `missing-styles.css` に差し替えたコピーで走らせても、結果は同じ `passed` / `exit=0` だった。**この検査スクリプトは、検査対象が壊れていても絶対に落ちない。**

日誌には最終行の `check.sh: ... passed` だけが引用されている。開発担当の実行環境に `rg` があったのなら意図的な誤報ではないし、その場合これは移植性の穴でしかない。だが**ループが実際に回るこの環境では動いていない**以上、直さなければならない。cycle 1 のレビューで私が評価したのは「動作確認していないことを正直に書いた」ことだった。今回はその逆で、**道具が本人の代わりに嘘をついている。**

### 2. `render-check.js` の偽 DOM は `index.html` を一度も読んでいない

`render-check.js` は `app/data/diary.json` と `app/app.js` しか読まない。セレクタの一覧（`ids` 配列、`entryFragment` の `selectorMap`）は**手で書き写した `index.html` の写し**であり、本物とは繋がっていない。

実証した。`index.html` の中身を `<!DOCTYPE html><html><body></body></html>` に丸ごと差し替えたコピーで `render-check.js` を走らせたところ、**そのまま `passed` / `exit=0` で通った。** ブラウザでは確実に真っ白になる状態が、検証を通過する。

今この瞬間はズレていない（`app.js` が引く 17 個の `#id` はすべて `index.html` に存在することを私も突き合わせた）。だが**それを保証している仕組みは何も無く、開発担当の注意力だけが担保になっている。** 日誌の「DOM を増やすならスタブも同時に追従させる」という申し送りが、まさにその手作業の存在を証明している。今回捕まえたバグ（消した復元ボタン）を捕まえられたのは、たまたまスタブ側を先に直したからで、逆順なら擦り抜けていた。

問題点1と2は同じ病気である。**この2本はこのループの免疫系であり、免疫系が偽陽性を返すなら、残り5サイクルで積み上げるものすべてが検証されないまま積み上がる。**

### 3. 日記が増えていく前提の読み体験が、まだ何も無い

現在5件。cycle 7 が終われば 22 件前後、本文込みで数万字になる。いまの画面は全件を古い順に縦一列に並べるだけで、検索も、サイクルへのジャンプも、折りたたみも、返信の枝を辿る導線も無い（返信リンクは「過去に遡る」一方向のみで、「この頁に誰が返事したか」は画面から分からない）。

**この日記は、このプロダクトの主役の一つである**（`docs/product-brief.md`「むしろこちらが主役かもしれません」）。その主役が読みにくくなっていく方向に、いま毎サイクル確実に進んでいる。cycle 1 から `TASKS.md` の「保留中」に置きっぱなしになっており、そろそろ順番が来ている。

### 4. 画面の一番上が「書く」フォームで、日記本文がその下に押し出されている

`index.html` の構成は hero →「書く」フォーム →「読む」→ 本文。日記帳を開いた人が最初に見るのが入力欄で、肝心の頁は下にスクロールしないと出てこない。読み物としてのプロダクトなのに、読み物が二番目に置かれている。設計判断としてありえない配置ではないが、**意図的に選んだのか、実装順にそのまま並べただけなのかが分からない。** 後者なら直すこと。

### 5. 「書き手」を増やせない

投稿フォームの書き手セレクトは `members` から `owner` を除いた3人に固定されている（`app.js:115`、`app.js:281`）。つまりこの日記帳を手に取った4人目は、**dev / feedback / slides の誰かになりすます以外に書く方法が無い。** product-brief の最低要件「複数人の書き手を区別して扱えること」は正本の表示側では満たしているが、書き込み側は3人に閉じている。`owner` が投稿できないのも、意図なら理由が要る。

### 6. `localStorage` への保存に失敗したとき、画面の状態と保存内容がずれる

削除ハンドラ（`app.js:341-346`）と復元ハンドラ（`app.js:349-354`）は、`localEntries` を先に書き換えてから `safeWrite` を呼び、失敗すると再描画しないで戻る。エラーは出るが**メモリ上は「削除済み」で保存領域は「未削除」**という状態が残る。その後フィルターを押すなど別の再描画が走ると、保存されていない削除が画面に反映され、リロードで復活する。投稿ハンドラ（`app.js:300-302`）は書き込み成功を確認してから状態を進めており正しい。削除／復元も同じ順序に揃えること。

### 7. `check.sh` が外部コマンド（`rg` / `jq`）に依存している

「依存パッケージは原則ゼロ」は実行時の制約であって開発ツールには直接かからないが、`rg` は標準では入っていない。問題点1を直すついでに、`node` と POSIX 標準コマンドだけで完結させるか、少なくとも**依存コマンドの存在を先頭で確認して無ければ落とす**こと。

### 8. ダークモード未対応（`color-scheme: light` 固定）

cycle 1 から据え置き。優先度は低い。ただし7サイクル分の長文を読ませるアプリではある。

## 野心判定への注記

RAISED と判定したが、**バーが上がっている方向が1本に偏っている**ことは指摘しておく。

cycle 1 → 2 は「読む」から「書く」への飛躍だった。cycle 2 → 3 の宣言（返信付きローカル投稿＋エクスポート／インポート）は、難度としては確かに上（トランザクション、ID 衝突、スキーマ検証）だが、**軸は「`localStorage` のデータ配管」のまま**である。一方で「読む」側は cycle 1 の一覧から一歩も動いておらず、問題点3のとおり毎サイクル悪化していく。

そしてもう一つ。このアプリは**かわりばんこ**という名前なのに、**まだ誰も順番に回していない。** 全員が同じ静的 JSON を読み、端末内の投稿はその端末で死ぬ。エクスポート／インポートは開発担当自身が出した答えで、方向は正しい。だが「ファイルを書き出して渡す」で止めると、それは日記の受け渡しではなく単なるバックアップになる。**「いま誰の番か」「自分の番が回ってきた」という、この製品の名前そのものの概念が、まだ画面のどこにも存在しない。** これは機能の不足ではなく、まだ誰も手を付けていない中心の空白である。

`TASKS.md` に具体化して置いた。

## 次サイクルへの指示

`TASKS.md` に優先度順で書いた。要点だけ:

- **タスク1と3（検証ツールの修理）を最初に、そして短く終わらせること。** これは「安全な微修正」に見えるかもしれないが違う。**壊れた検証を抱えたまま機能を積むのが、このループで最も高くつく。** ただしここに1サイクル使ったら本末転倒なので、合わせて数時間で切り上げ、残りは全部タスク2に注ぐこと。
