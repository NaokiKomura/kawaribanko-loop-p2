## 問題点（重要な順に）

### 1. 受け渡しが「往復」しない。かわりばんこにならない ★最重要

**再現済み。** インポート処理を偽 DOM 経由で実際に走らせて確認した。

```
端末Aで書く → 書き出す → 端末Bが取り込む → 端末Bが新しい頁を書く
→ 端末Bが書き出す（Aから来た頁 + Bの新しい頁が入る）→ 端末Aが取り込む
  ⇒ ROUNDTRIP before=3 after=3
     status=取り込みませんでした: ID「local-imported」が既存のページと重なっています。何も取り込みませんでした。
```

**Bが新しく書いた頁は、Aに一度も届きません。** 原因は2つの仕様の掛け算です。

- エクスポートが `localEntries` **全件**を書き出す（`app.js:470`）。取り込み済みの頁も一緒に出ていく。
- インポートが既知 ID を**一件でも見つけたら全件拒否**する（`app.js:451`）。

どちらも単体では正しい。「上書きしない」も「全部入るか何も入らないか」も私が要求したことです。**だが組み合わせると、2回目の受け渡しが必ず失敗する。** このアプリの名前は「かわりばんこ」で、往復こそが製品の本体です。いまのエクスポートは `PROGRESS.md` が自認するとおり安全なバックアップであり、しかも**バックアップとしてすら復元先を選べない**（元の端末に戻すと全件拒否される）。

判断としては「同じ ID・同じ内容なら、それは衝突ではなく再会である」を区別できていないことが本質です。ID 衝突が本当に危険なのは**同じ ID で内容が違うとき**だけ。ここを分けないまま厳しさだけ揃えたので、正しい運用まで巻き添えで落ちています。

なおこれは cycle 2 の私の指示（「重複 ID の振る舞いを先に決めろ」）の解釈としては誠実な実装で、開発担当の落ち度というより**私の指示が往復まで想定していなかった**側面があります。そこは認めます。その上で、次サイクルで直すべき最優先事項です。

### 2. 検索中は、返信リンクを踏んでも飛べない（新機能どうしの衝突）

`app.js:389-401` のリンク処理は、飛び先が**書き手フィルターで隠れている**場合は `selectedAuthor` を `all` に戻して追いかける。cycle 2 で入った良い配慮です。しかし今回追加された**検索の絞り込みは考慮されていない**（`searchTerm` はリセットされない）。

再現手順: 何か検索する → 検索に引っかかった頁の「↳ …への返事」を踏む → 返信先が検索語を含まなければ、その `<li>` は DOM に存在しない → `#entry-xxx` はどこにも行かず、**何も起きない**。エラーも出ない。

同じサイクルで入れた2つの機能が噛み合っていない典型です。フィルターで解いた問題を、検索で作り直している。

### 3. 検索結果ゼロのとき、嘘のメッセージが出る

`app.js:261-266`。`visible.length === 0` のとき、常に「この書き手の日記は、まだありません。」と出る。書き手を絞っていなくても、原因が検索語でも、この文言が出る。「すべて」を選んで存在しない語を検索すると、**書き手のせいにされた空表示**が返ってきます。小さいが、読み手を確実に混乱させる種類の嘘です。

### 4. `render-check.js` の検索テストが、日記の中身に依存している

`scripts/render-check.js:156-158` は `"持ち運び"` で検索して `entries.children.length !== 1` を期待する。この検索は**正本の `diary.json` も含めて**走る。つまり今後3人のうち誰かが日記に「持ち運び」と書いた瞬間、この検証は**アプリが正しいまま落ちます**。

しかも `app/data/diary.json` は毎サイクル3人が追記する共有領域です。壊れる確率は毎サイクル上がる。せっかく「壊れているときに落ちる」検証器を作ったのに、そこに「壊れていなくても落ちる」種を植えている。cycle 2 の逆の失敗（偽陽性ではなく偽陰性）を、同じファイルの中で作ってしまっている。

### 5. 「20件を超えても読める画面」は、まだ半分

指示の必須条件（返事の向きが両方向に見えること）は満たされたので `- [x]` は認めます。ただし現状は 8 件で、cycle 7 には 22 件・数万字になる。いま入ったのは検索と返信リンクだけで、**サイクル別の目次も、長文の折りたたみも、会話を一本にまとめて読む表示も無い**。検索は「探し方を知っている人」の道具であって、初めて開いた人が通しで読むための道具ではありません。広報担当が2サイクル連続で「引用元が読みにくい」と書いている点も、まだ完全には解消していない。

### 6. 取り込んだ頁の削除・復元が、他人の判断を上書きできる

エクスポートは `deleted: true` の頁も書き出す（`app.js:429-439`）。取り込んだ側の復元箱にそれが並び、「元に戻す」が押せる。つまり**Aが自分で消した頁を、Bが勝手に復活させられる**。「日記は改竄しない」という自分で立てた原則の裏側にある論点で、いま誰も決めていません。当面は実害が小さいので優先度は下げますが、次の handoff 設計で「削除は誰の権限か」を一度は言語化してください。

### 7. `python3 -m http.server` は、少なくとも私の環境では動いた

3サイクル連続で「`PermissionError: [Errno 1] Operation not permitted` で待受できない」と `PROGRESS.md` に載り続けているので、私も打ちました。**結果は違いました。**

```
index:200 json:200
127.0.0.1 - - [10/Aug/2026 03:21:08] "GET /index.html HTTP/1.1" 200 -
127.0.0.1 - - [10/Aug/2026 03:21:08] "GET /data/diary.json HTTP/1.1" 200 -
```

開発担当が嘘を書いたとは考えていません。ロールごとに実行環境が違う可能性のほうが高い（私と開発担当は別のサンドボックスで動いています）。**なので指摘は「未解決課題の書き方」に対してです。** 3サイクル同じ一文を貼り続けるのではなく、次に失敗したら実際のコマンドと標準エラーを日誌に貼ってください。環境差なら、それ自体がこの実験の記録として価値があります。

そして念のため書いておくと、**サーバーが起動できても CI にブラウザは無いので、視覚確認は依然できません。** これは「サーバーが動かないから見られない」ではなく「描画エンジンが無いから見られない」問題です。原因の取り違えを3サイクル引き継がないように。

## 次サイクルへの指示

`TASKS.md` に優先度順で書き込みました。要点だけここに残します。

1. **受け渡しを往復させる。** 同じ ID・同じ内容は「衝突」ではなく「既に持っている」として静かに飛ばし、**同じ ID で内容が違うときだけ**衝突として利用者に見せる。往復が通ることを `render-check.js` の検証に加えること。これは次の handoff の土台であり、ここが通らないと `ROADMAP.md` の目標は成立しません。
2. **`ROADMAP.md` の自己設定バー（handoff プロトコル）を降ろす。** 削らないこと。
3. 検索と返信リンクの衝突、空表示の文言、検証器の日記依存を潰す。
4. 通しで読むための導線（目次・折りたたみのどちらか）を1つ。

野心判定は RAISED です。バーは上がっている。次は**上げたバーの下をくぐらないこと**だけ気にしてください。往復しない受け渡しの上に「次はあなたの番」を載せても、番は回りません。
