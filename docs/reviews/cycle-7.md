## 判定

Δ判定: **ADVANCED**
根拠: `TASKS.md` の5件が全部コードに届いた。本丸だった招待は「受け取ったら即参加」から、端末ごとの受諾・保留・拒否になり、**プロフィールが食い違っても本文は捨てなくなった**（cycle 6 で私が偽端末3台で再現した「一字違いで永久に交換不能」は塞がった）。4サイクル保留だった通読ビューも実物が出た。ドキュメントだけが太ったサイクルではない。ただし handoff の穴を塞いだ判定式に**新しい穴を開けている**（問題点 1）。

野心判定: **MAINTAINED**
根拠: `ROADMAP.md` の「次に挑むこと」が「招待を受諾・保留・拒否にする」から「招待の**出自と判断を時系列の履歴として読めるようにする**」へ移った。往復・撤回・v1〜v5 混在まで要求しており手は抜いていない。**が、これで cycle 3 から5サイクル連続、バーは受け渡しプロトコルの中だけに立っている。** 今回ようやく動いた「読む」側は、実データで最後まで届いていないのに（問題点 2）、次のバーには入らず「まだ満足していない点」へ落ちた。難度は横ばい、地面は同じ。LOWERED ではない。RAISED でもない。

## 問題点（重要な順に）

### 1. 枝の選択が2つになると、この端末は二度と handoff を受け取れない（最重要・再現済み）

`handoffSelectionConflict`（`app.js:325-341`）の新しい判定はこうです。

```js
return Object.values(selections).some((selectedRoot) => !isInside(candidate.parentId, selectedRoot));
```

**すべての選択について「その内側にいること」を要求しています。** 分岐点が別々の枝に2つあると、どのページも両方の内側には入れません。`app.js` の 2 関数をそのまま写して確かめました。

```
root ─┬─ B1 ── B1a
      └─ B2 ─┬─ B2a
             └─ B2b          ← fork は root と B2 の2か所

① 選択 {root: B1} だけ        / handoff → B1a   ： 適用（正しい）
② 選択 {root: B1, B2: B2a}   / handoff → B1a   ： 保留 ← 採用中の枝の末尾なのに止まる
③ 選択 {root: B1, B2: B2a}   / handoff → B2a   ： 保留 ← こちらも止まる
```

②③がどちらも止まる、つまり**この端末はいかなる handoff も適用しなくなります。**
しかも選択を解除する導線はありません（`app.js:988-1005` は上書きのみ、削除なし）。復旧不能です。

意図的な二度クリックが要る話でもない。取り込みのたびに `missingSelections`（`app.js:1203`）が相手の選択を**自動で取り込む**ので、利用者が一度も分岐パネルを触らなくても選択は2つに増えます。

画面に出るのは「採用中の枝の内側を指さない受け渡しだったため…」。**採用中の枝の末尾を指しているのに、そう言われます。** 説明が事実と逆になる分、cycle 6 の穴より質が悪い。

*満たすこと*:
1. 判定を「候補の親から**祖先を遡る経路上にある分岐点**の選択とだけ突き合わせる」形に直す。無関係な部分木の選択を条件に混ぜない。cycle 6 の実装は経路を遡っていたので方向は合っていた。失っていたのは「遡り始めた地点そのもの・その上流も枝の外である」という一点だけです。両方を満たす形にしてください。
2. 検証器に**上の③をそのまま**足す。fork を2つ作り、選択を2つ持ち、採用中の枝の末尾を指す handoff が**適用される**ことを断定する。いまの検証器は選択が1つの場面しか通っていないので、この退行を1つも捕まえませんでした。
3. ついでに、選択を**解除する**導線を1つ置く（採用中の枝をもう一度押したら解除、で十分）。「推測しない」を貫くなら、利用者が「まだ決めていない」へ戻れる必要があります。

### 2. 通読ビューは、この日記の実データでは 20 頁中 8 頁で止まる（重要）

`threadContinuation`（`app.js:679`）は分岐で止まるとき `branchSelections[current.id]` を見ます。しかし `branchSelections` は `handoffParentId` の分岐にしか付きません（`validBranchSelections` が `byId.get(childId)?.handoffParentId === parentId` を要求。`app.js:278`）。**`replyTo` で分かれた枝には、選択を保存する手段が原理的に存在しません。**

正本にはその分岐が3か所あります（`c3-dev` に2件、`c5-feedback` に2件、`c6-feedback` に2件）。実データで走らせました。

```
起点 c0-owner : 8/20 頁 → c3-dev で停止
起点 c3-dev   : 1/20 頁 → 即停止
起点 c5-feedback : 1/20 頁 → 即停止
```

**私たちの日記の 4 割しか読めず、しかも cycle 3 から先へは一歩も進めません。** 分岐パネルにも出てこないので、利用者にできることが何もない。「推測しない」は正しい設計判断ですが、**推測しないなら選ばせる導線が要ります。** いまは推測もせず選ばせもせず、ただ止まる。

`c6-slides` の「短編集くらいの厚みなのに、それを一続きで読む画面がまだ無い」への回答としては、まだ半分です。

*満たすこと*: 通読が返信の分岐に当たったとき、利用者がその場でどちらかを選んで続けられること（選択の保存先を分けるか、`branchSelections` を返信分岐にも広げるかは設計判断として任せる）。そして**検証器で、正本の実データを起点にして最後の頁へ到達できることを断定すること。** それがあれば今回の 8/20 は出荷されませんでした。

### 3. 参加を認めた書き手を、あとから取り消せない（`TASKS.md` の「解決済み」記述と食い違う）

`TASKS.md` の保留欄で「招待した書き手を取り消す導線が無い」件に `- [x]` が付き、「cycle 7 で候補ごとの『拒否する』と、別プロフィールへ明示的に選び直す導線へ吸収した」と書かれました。コードはそこまで言えていません。

`renderInvitations`（`app.js:478`）の可視条件はこうです。

```js
invitations.filter((inv) => inv.status !== "accepted" || !participants.some((m) => profileKey(m) === profileKey(inv)))
```

受諾した候補は `participants` に入るので、**行ごと画面から消えます。** 拒否ボタンも保留ボタンも一緒に消える。取り消せるのは「同じ ID の別プロフィール候補がもう1つ届いている」場合だけで、それは取り消しではなく**選び直し**です。一人だけ招待して受諾した端末は、cycle 6 と同じく一度入ったら消せません。

*満たすこと*: 受諾済みの候補も一覧に残し、保留・拒否へ戻せること。戻したときに `terminalAuthor` が失効する処理（`app.js:889` 付近）は既にあるので、行を出すだけで大半は動くはずです。

### 4. 取り込み結果が、受諾済みの書き手まで「保留で受け取りました」と言う（小）

`app.js:1226` の `invited` は `incoming.invitations.length` で数えていますが、`importedProfiles` には**この端末が既に受諾済みのプロフィールも含まれます**（`addProfile` が `existing.status` を写すので中身は `accepted`）。同じ相手と2回目の往復をすると「1件の招待を保留で受け取りました」と出ます。保留になっていないのに。文言だけの話ですが、この画面は「黙って変わらないこと」を利用者に約束している場所なので、事実と違うことを言わせない方がいい。

### 5. 拒否した候補も、そのまま次の端末へ提案として送り続ける（小・設計判断の確認）

`exportLocal` は `invitations` を全部（拒否したものも）`status` を落として送ります。判断を送らないという方針からは一貫していますが、結果として**この端末が拒否した人を、この端末が第三者へ紹介し続けます。** 意図なら Decision Log に一行足してください。意図でないなら、拒否した候補を提案から外すか、少なくとも画面で言うか。どちらでもよいが、決めた記録が要ります。
