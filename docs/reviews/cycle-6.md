## 問題点（重要な順に）

### 1. 分岐の**親そのもの**を指す handoff は、いまも選択を黙って無効化する（中）

今回いちばん大事だった修正に、穴が残っています。`handoffSelectionConflict()`（`app.js:279`）は `handoff.parentId` から**親を遡って**、選択と食い違う枝に属するかを見ます。だから「兄弟枝の頁を指す handoff」は正しく止まる。止まらないのは、**分岐の親そのもの（またはその上流）を指す handoff** です。遡り始めた地点が既に分岐点なので、食い違う枝に一度も出会いません。

C 枝を採用中の端末に、`handoff.parentId = local-a`（分岐の親）のファイルを流した実測です。

```
取り込み前  選択: C 枝 / 番: いまは 🛠️ 開発担当さん / 次の頁がぶら下がる親: C 枝の末尾
   ↓ 新規0件・再会1件のファイルを取り込む（handoff は分岐の親 local-a を指す）
取り込み後  選択: C 枝 / 番: いまは 🔍 レビュー担当さん / 次の頁がぶら下がる親: local-a
   #turn-notice hidden: true                        ← 何も出ない
   取り込み結果: 「0件を取り込みました、再会した1件はそのままにしました。」← 番の話が一言も無い
   分岐パネル: 「B の枝」 || 「C の枝（採用中）」    ← 採用中と言い続ける
```

cycle 5 に私が書いたのと**同じ形**です。画面は C を採用中と言い、次の頁は分岐の手前にぶら下がる。しかもこの端末が次に書くと、`local-a` から**3本目の枝**が生えます。利用者は C の続きを書いたつもりでいる。

日誌には「同じ端末の選択を handoff より上位に置いた」と書いてあります。Decision #11 も「既存枝選択と食い違う受信 handoff は適用せず、選択を優先する」。**この2行が言っていることと、コードが守っている範囲が一致していません。** 実装は「食い違う枝を指す handoff」だけを止めていて、「選択を無意味にする位置へ番を戻す handoff」は素通しです。

規模は小さい（判定を1つ足すだけ）。優先度が高いのは、これがあなたが今サイクル自分で引いた線だからです。

### 2. 招待の衝突が、二台を**永久に**交換不能にする（中）

プロフィールの全件拒否は正しい設計です。ただし**復旧手段がありません**。招待を取り消す UI が無く、`kawaribanko.participants.v1` に一度入ったプロフィールは消せない。結果、typo 一つで往復が死にます。

```
端末 X: mika を「みか」で招待 → 頁を1つ書く
端末 Y: mika を「ミカ」で招待 → 頁を1つ書く   （タイプミスでも起きる）
X ← Y : 取り込みませんでした: 書き手ID「mika」は 表示名 が既存のプロフィールと食い違います。
Y ← X : 取り込みませんでした: 書き手ID「mika」は 表示名 が既存のプロフィールと食い違います。
Z ← X : OK（Z は みか を採用）
Z ← Y : 取り込みませんでした。 ← Z も Y と縁が切れる
```

**本文まで巻き添えです。** 「みか」と「ミカ」の一字を巡って、二人が書いた日記が永久に相手に届かない。しかも画面は直し方を教えてくれない（招待を消す導線が無いので、直しようがない）。

これは設計が間違っているのではなく、**設計が半分しかない**ということだと思います。あなた自身が `ROADMAP.md` に書いた「受諾・保留・拒否」と「本文を捨てない」が、まさにこの穴です。次サイクルの本丸で片付けてください。

### 3. 端末の役割が「書く」フォームに届かない（小・実ブラウザでのみ起きる）

`renderTerminal()` と `renderReplyOptions()` は `replaceChildren` の前後で `value` を退避・復元しています。`renderAuthors()`（`app.js:311`）だけ、していません。

```js
const renderAuthors = () => {
  ...
  elements.author.replaceChildren(fragment);   // ← 復元が無い
};
```

実ブラウザで `<select>` に `replaceChildren` すると、選択は先頭の option（＝ `開発担当`）に落ちます。起こることは2つ。

- **起動直後**: 役割を `📣 広報担当` にしてページを開き直すと、カードは「この端末は 📣 広報担当として名乗っています」と出るのに、「書く」の書き手欄は `🛠️ 開発担当` を指している。役割を反映するのは `change` ハンドラだけで、起動時に `elements.author.value` を合わせる箇所がありません（偽 DOM でも起動後の値が空のままなのを確認しました）。
- **取り込み直後**: 今サイクルから import の中で `renderAuthors()` を呼ぶようになりました。自分を選んでから取り込むと、書き手欄が黙って `開発担当` に戻ります。

「あなたの番です」と言われた人が、そのまま書くと**他人の名前で投稿されます**。名乗り機能の価値をいちばん素朴に削る場所です。

なお、これは**偽 DOM では原理的に捕まりません**（`FakeNode.value` はただのプロパティで、`replaceChildren` の副作用が無い）。検証器の限界がはっきり出た1件なので、直すときは「`replaceChildren` する `<select>` は必ず `value` を退避・復元する」という形で、`renderReplyOptions()` / `renderTerminal()` と揃えてください。

### 4. 「検証器が正本に依存しない」の自己防衛が、まだ描画1件ぶんしかない（小）

`render-check.js:285-288` は正本に1件足した偽日記で `boot()` し直しますが、確かめているのは `#entries` の件数だけです。その後の**シナリオ（v1〜v4、分岐、役割、招待、衝突）は一度も偽日記で走りません**。誰かが `diary.entries[3].title` に依存する断定を書いても、この試験は素通しします。

念のため私が手で、(a) 日記を2件足した正本、(b) 書き手を全員改名して4人目を足した正本、の2通りでフルに走らせました。**どちらも通ります。** 実力としては大丈夫です。守りが薄いだけ。……ただ、これで私が正本をいじって手で確かめたのは3回目です。4回目はやりません。

### 5. 設定カードが、日記より先に来た（小・ただし設計の一貫性の話）

`index.html:19-41`。`.terminal-card`（見出し＋説明2行＋セレクト＋状態＋招待の `<details>`）が hero の直後、`次の番` より**上**に入りました。cycle 2 から4サイクルかけて「読む場所を上げてほしい」と言い続け、cycle 5 でようやく返ってきた負債の一部を、その次のサイクルで借り直しています。

役割は「たまに変える設定」、日記は「毎回読むもの」です。頻度が逆になっている。加えて、この並びは**誰も実物を見ていません**。6サイクル通して、このアプリの画面を人間もエージェントも一度も見ていない。だから並びの善し悪しは議論できず、**文書順という機械が読める形で守る**しかない。そこは検証器で固定できます（次サイクルの指示に書きました）。
