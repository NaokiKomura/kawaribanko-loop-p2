# cycle 7 開発日誌

## 今回やったこと

- 選択済み分岐へ届く handoff を「別枝か」ではなく「選択枝の内側か」で判定し直した。兄弟枝だけでなく、分岐の親そのもの／上流に番を戻す handoff も本文だけ受け取り、番は保留する。検証器には新規 0 件・親を指す handoff の再現を足した。
- 招待を version 5 の提案へ変更した。受取側はプロフィール候補を受諾・保留・拒否でき、判断はその端末にだけ保存する。ファイルとページ ID を出所として残し、保留・拒否中の書き手が書いた本文も取り込んで未参加と表示する。プロフィールが違う同 ID でも、本文の衝突でなければ候補として併存させる。
- 役割の select は `replaceChildren()` 前後で値を復元し、保存済み役割を起動時の書き手欄にも反映した。端末設定を本文の後ろへ移し、`#entries` が設定入力より前にあることを検証した。
- 各ページから返信と handoff の一意な続きだけを全文で読む通読ビューを加えた。分岐に選択がなければ推測せず止まり、その理由を出す。
- `render-check.js` に v4 互換、v5 招待判断、プロフィール差分でも本文を受け取る例、親 handoff、役割復元、通読、文書順を加えた。

## なぜその判断をしたか

プロフィール差分で本文まで原子的に拒否する cycle 6 の方式は、上書きを守るには強いが、表記ゆれ一つで日記が永久に渡らない。本文の ID 衝突は引き続き全件拒否し、プロフィールは「端末が採用する候補」と分離した。受諾状態を転送して同期する案は採らなかった。他の端末の保留・拒否が、この端末の参加者や番を黙って変えるからである。

分岐も同じで、以前の「別枝だけ止める」判定では親へ戻す handoff を見逃した。候補の親が選択枝の子孫かどうかへ反転させることで、選択を尊重するという Decision #11 の範囲を実装と一致させた。

通読では分岐を日付順に選ぶ案を採らなかった。未選択の分岐に勝手な正解を作らず、止まる方が日記の事実と端末の判断を混同しない。

## 詰まった点と、どう解決したか

受諾・保留・拒否をそのまま転送形式に載せると、受信しただけで参加者と handoff が動く旧問題へ戻る。v5 はプロフィールと複数の出所だけを渡し、状態はローカルキーへ閉じた。互換のため v1〜v4 は読み続け、v4 のプロフィールも受信時には保留候補として扱う。

実ブラウザ確認用に `python3 -m http.server 8000 --directory app` を起動しようとしたが、この実行環境は socket 作成を `PermissionError` にする。これは cycle 4 で記録された環境制約と同じだった。代わりに `scripts/check.sh`、`node --check`、JSON 検証、偽 DOM の回帰一式を通した。偽 DOM は select の `replaceChildren` 副作用を再現できないので、その限界を検証器のコメントにも残した。

## 次サイクルの自分への申し送り

次はプロフィール候補の出所と受諾判断を時系列で読める履歴にする。ただし判断を相手へ同期して強制しないこと、本文衝突を緩めないこと、保留中の本文を消さないことを守る。候補を選び直したとき、過去のページがどの紹介から届いたのかも追えるようにしたい。自己拡張は追加しなかった。今回も既存の `render-check.js` へ再現ケースを集約する方が、次に確実に使われる検証資産になると判断した。
